Overview
Purpose and Scope
This document specifies the functional requirements for the Case Management System (CMS) component of the SDC Island Integrated Operations Centre platform, covering 
Incident Management
Fault Reporting
Task Management
Broadcast and Notification
CMS Dashboard
System Configuration and Administration
CMS Modules
The CMS is a web browser-based platform. All modules are subject to role-based access control; the specific modules, tabs, and functions visible to a given user upon login are determined by their assigned role. The following modules are covered in this document.
Module
Description
Incident Management
Creation, assignment, tracking, and closure of incident records from all reporting sources across the island
Fault Reporting
Creation, automatic triage, routing, and closure of infrastructure fault records, with rule-based assignment to the appropriate IFM contractor and CMMS ticket creation via API where required
Task Management
Assignment and tracking of operational tasks directed to Rangers or SDC staff, linked to a parent Case
Broadcast and Notification
Structured framework for disseminating incident information to defined distribution groups, with crisis-level classification governing escalation and recall behaviour
CMS Dashboard
Consolidated operational view of active cases, incidents, faults, and tasks, with a filterable 2D map of island-wide activity
System Configuration
Administration of user accounts, role assignments, classification taxonomies, routing matrices, distribution groups, and audit settings
Authentication and Access Control
Authentication Method
Users authenticate to the CMS via Whole-of-Government Single Sign-On (WOG SSO). Two-Factor Authentication (2FA) is enforced for all user accounts. Access granted via WOG SSO may assign users a default role with minimal permissions, such as fault submission and status tracking, without requiring a separately provisioned CMS account
CMS Dashboard
The CMS Dashboard shall provide a consolidated operational view for Controllers, Duty Officers, and Duty Managers.
It is distinct from the UCS Dashboard in scope and purpose: the UCS Dashboard presents live-state summary counts and high-level situational awareness, while the CMS Dashboard provides access to both current and historical records with line-item detail views.
Landing Page and Navigation
Upon successful authentication, users are presented with the CMS landing page. Navigation items visible to a given user are filtered by their assigned role.

2D Island Map
The CMS Dashboard shall include an embedded 2D map of Sentosa Island leveraging on OneMap and its available API. The map will provide a consolidated spatial view of active operational activity across the island and is accessible to all users with Dashboard access.
Map Layer
Description
Incidents
Drop-pins for active and recent incident records, derived from the text-entered location data on each incident log. Coordinates are resolved from the entered address, road name, building, or postal code via the OneMap geocoding API
Faults
Drop-pins for active fault records, resolved by geocoding
Active Works
Boundary overlays for approved and active NOP works areas. Works boundaries drawn by NOP applicants during their application are automatically displayed on this map upon permit approval, providing Controllers with a live spatial overview of all ongoing permitted works on the island
Geographical filtering shall be constrained to Sentosa Island, preventing drop-pins or overlays from being plotted outside the island boundary.
For locations with defined physical boundaries, such as named buildings and venues, the system shall associate a text-entered location with the corresponding pinned coordinate.
For road-based locations, which cannot be geofenced, coordinate resolution relies on the geocoding result returned by OneMap for the entered road name or common name.
Island events at fixed venue sites, such as pavilions, event grounds, and beaches, shall be represented on the map as drop-pin icons.
Integration with Unified Command System
The CMS and the Unified Command System operate as complementary but functionally distinct platforms.
While the CMS is the system of record for all operational case data, the UCS is the primary command interface, surfacing a real-time operational overview to Controllers and the Duty Officer.
Live Metric Feed to UCS Dashboard
The CMS shall supply real-time summary counts to the UCS Dashboard, including the number of active cases, open incidents, open faults, active tasks.
Summary counts shall update in real time as records are created, updated or closed in the CMS. 
Detailed record lists and case-level views are not replicated on the UCS and reside exclusively within the CMS.
Embedded CMS Functions within UCS
CMS functions that are frequently used or operationally time-critical shall be surfaced as embedded panels or inline actions within the UCS, without requiring the user to navigate away from the UCS interface.
Actions performed through embedded UCS panels shall create, update, or retrieve records directly in the CMS. The UCS does not store or duplicate CMS data.
The embedded functions shall operate under the same role-based access controls as the full CMS.
Incident creation is a mandatory embedded function. A Controller shall be able to create a new Incident record from within the UCS without navigating to the CMS. See Section 2.5.3. 
Note: The full list of CMS widgets/items to be made available as embedded widgets on the UCS dashboard is still under discussion with SDC.
Navigation from UCS to CMS
When a Controller or Duty Officer selects a live metric or summary item on the UCS Dashboard, navigation directs the user to the corresponding CMS module page rather than a UCS sub-page.
Line-item detail, record views, and case editing are handled entirely within the CMS and not replicated in the UCS.
Navigation from UCS to CMS
Where a function is not available as an embedded UCS action, selecting a live metric, summary item, or record reference in the UCS shall direct the user to the corresponding CMS module page.
Line-item detail, full record editing, case management, and reporting functions are handled within the CMS and are not replicated in the UCS.
Incident Creation from UCS
A Controller shall be able to initiate a new Incident record directly from the UCS without navigating to the CMS.
Incident creation from the UCS shall be available as an inline action, for example in response to a Video Analytics alert, a system-generated prompt, or a patrol report received in the UCS.
The Incident record shall be created and stored in the CMS. The UCS surfaces the creation interface only; it does not own the record.
Where a Video Analytics alert or system prompt is used as the trigger, the relevant alert reference shall be pre-populated into the Incident record where applicable.
Upon successful creation, the Controller shall be able to continue monitoring the UCS or navigate directly to the full Incident record in the CMS.

Contextual Roles
Two roles are contextual, meaning they are determined by a user's relationship to a specific record rather than assigned at system level.
Owner
User who creates an incident or task record, typically a Controller. Owner permissions apply only to that specific record.
Responder
User assigned by the Owner or Controller to contribute field activity information to an incident or task. Responder permissions apply only to the specific record to which they are assigned.
Assigning a Responder is optional. A Controller may complete and submit a record without one.
Duty Officer Role Elevation
The Duty Officer may be elevated to cover Duty Manager responsibilities during the Duty Manager's absence. In the elevated state, the Duty Officer holds identical permissions to the Duty Manager. 
Note: Approach for activating this elevation, assigned per shift via duty roster or applied as a long-term role configuration on a named user is still to be confirmed.

Record Data Retention
When a user account is deactivated or removed, their associated records should remain accessible to users with appropriate role permissions, with the original creator's identity preserved on each record.
Case Data Model
The Case is the top-level record in the CMS. All operational activity is anchored to a Case.
Entity Structure and Relationships
A Case may be created independently of any child record.
A Case may contain zero or one Incident record.
A Case may contain zero or more Task records.
A Case may reference zero or more CMMS Ticket IDs. These identifiers are returned by the IFM CMMS upon ticket creation and stored as reference attributes of the Case. The ticket lifecycle is owned entirely by the IFM CMMS.
An Incident, Task, or CMMS Ticket reference cannot exist in the CMS without an associated Case.
Where a Case does not exist at the time of Incident or Task creation, the system shall auto-create a Case before creating the child record.
Occurrence records are standalone entries, not associated with the Case record structure.

Case ID and Naming Convention
System shall generate a unique identifier upon creation.
The Case ID follows the format YYYY/MM/NNNN, where YYYY is the four-digit year, MM is the two-digit month, and NNNN is a zero-padded sequential number resetting at the start of each month. 
The Case ID is referenced by all child records (Incident, Tasks) for traceability.
Case Status Definitions
Status
Description
Pending Triage
Initial status on Case creation. The Controller has not yet determined whether action is required
Active
Action has been determined as required. One or more sub-processes (Incident, Task, CMMS Ticket) are in progress
Closed
All linked Incident, Task, and CMMS Ticket records are resolved. The Case is read-only
The Controller may close a Case after a CMMS Ticket has been raised, without waiting for the IFM contractor to resolve the ticket.

Incident Management Module
The Case is the primary operational record container in the CMS. Every operational activity on the island, whether an incident, a ground response task, or an infrastructure fault requiring contractor action, is anchored to a Case record.
Incident Classification
Incident Types
Each incident record shall be assigned a Type and a Sub-type from SDC's defined classification taxonomy.
Both Type and Sub-type fields are mandatory.
Sub-type values are unique within each Type. An Others option shall be available as a Sub-type of last resort where no defined Sub-type accurately describes the incident.
Note: Finalised Incident Type and Sub-type taxonomy to be confirmed
Incident Categories
Beyond Type and Sub-type, the following operational categories apply to incident records and govern how they are handled within the system. These categories are for-info and not noted in the system.
Category
Description
Standard Incident
An active incident requiring Controller management and, where applicable, a Ranger field response
Proactive Incident
Created by the Controller in response to a notification or advisory where no immediate ground response is required. Common examples include missing person lookouts and lost item notices
Backdated Incident
Created to record an incident that has already occurred and concluded, typically following notification from a state agency after the fact. The record is created, populated with the known details, and closed immediately
Ongoing Incident
An incident that remains open over an extended period while the situation develops and is actively monitored. Common examples include prolonged state emergencies or extended search operations
Operational Record
An administrative record created for tracking purposes, covering planned exercises, drills, or coordinated information dissemination. These records do not require a ground response or broadcast
Crisis Incident Level Classification
Each Incident shall be assigned a Crisis Level at the point of creation or escalation by a Controller
The Crisis Level determines the broadcast type, distribution group, and escalation behaviour triggered upon or during the incident. 
The crisis level is assigned by the Controller at the point of incident creation and may be escalated by the Duty Manager or Duty Officer as the incident develops.
Note: Full classification and routing behaviour is defined in further sections on Broadcasts.

Incident Lifecycle
An Incident record shall be created either manually by a Controller or automatically triggered from a third-party source or the UCS.
Where a Case does not already exist, Case creation is triggered automatically before the Incident record is initialised.
The Controller may assign one or more Responders to the Incident. Assignment is optional; an Incident may be managed without a Responder assigned.
The Incident progresses through defined statuses reflecting its operational state.
Upon closure, the system shall automatically record the identity of the closing user and the closure timestamp.
Closed Incident records are read-only. A System Administrator must revert the status to an active state before any edits can be made.

Responder Activity Logging
The Responder Activity section is a dedicated segment within the incident record, separate from the Event Details section. It is accessible only to the assigned Responder and is used to log the actions taken during the ground response.
Responders shall be able to log activity updates against an Incident
Selection of activity list should support typing for free-text, but also support auto-complete from a predefined activity list to guide Responders to quick-fill
Activity log entries are timestamped and attributed to the logging user.
Activity logs are read-only once submitted and are not editable by the Responder.
Activity log entries are visible to Controllers and Duty Managers in the Incident record view.
Duplicate Incident Detection and Handling
Multiple reports of the same incident may be received concurrently from different sources, e.g. several guests calling the 1800 hotline about the same event within a short period.
The system shall flag the Controller when a potential duplicate incident is detected during manual creation, based on matching criteria including date, time, incident type, and sub-type.
The Controller retains the option to proceed with creating a new record, override the duplicate flag, or link the new record to an existing incident
Where a record is confirmed as a duplicate, it shall be marked as a linked duplicate and not treated as an independent active Incident
Linked duplicates shall not generate independent response workflows or separate broadcast triggers
Closing the Master Incident shall automatically close all linked duplicate records. 
Incident Record Save and Concurrent Editing
Save Mechanism
The system shall auto-save all form input at regular intervals while an incident record is being edited, to minimise data loss in the event of session timeout or interruption.
A manual save action shall also be available to the user at any point during editing.
A record in an unsaved state shall display a visible indicator to the user.
Unsaved changes shall not be discarded without user confirmation.
The auto-save interval shall be configurable by the System Administrator.
Concurrent Editing
Where two Controllers access and edit the same incident record simultaneously, the system shall manage the conflict to prevent one Controller's saved input from silently overwriting the others without notification. 
Scenario
Required Behaviour
Second user opens a record already being edited
The system shall notify the second user that the record is currently being edited by another user
Both users save changes to the same record
The system shall not silently discard either user's input. A conflict resolution mechanism shall be applied to surface the discrepancy and prompt resolution
Linked Fault Creation
Where an incident reveals an underlying infrastructure defect, a Fault Report may be created directly from the incident record.
A Controller may raise a fault record from within an active Incident where physical defect is identified as part of or resulting from the incident.
Fault creation from an Incident record shall initiate the CMMS ticket creation workflow
The fault record shall be linked to the originating incident and shall be visible from both the incident and fault detail views.
The incident and fault are managed independently once created. Either may be closed before the other.
Incident may be closed after the immediate situation is resolved while the fault record remains open as the infrastructure repair and investigation continue.
False Alarm Handling
Where an incoming report or VA alert is reviewed by the Controller and determined to require no action, the Controller may log the record and mark it as a false alarm.
A false alarm record, including the identity of the closing user, shall be retained in the system as a closed record for audit and reporting purposes.
Incident Closure and Reopening
Incident closure requires Duty Manager or designated in-charge approval, except for false alarm closures
A Controller shall submit an Incident for closure by transitioning it to Pending Review status
The Duty Manager shall review the record and either approve closure or return it with comments.
Upon approval, the Incident status changes to Closed and the Case closure process is triggered if all linked records are resolve.
To reopen a closed incident, a System Administrator must revert the status from Closed to the appropriate active status.
Upon closure, the system shall automatically trigger a closure broadcast.
Broadcasting Triggers
Broadcast specifications including delivery channels, templates, recipient group management, crisis level classification, and the routing matrix are defined in Section 10: Broadcast and Notification Framework.
Closure Broadcast
The system shall automatically trigger a closure broadcast when the Duty Manager or designated In-charge approves incident closure.
The system shall dispatch the broadcast to the configured recipient group without requiring a separate manual send action from the Controller.
One closure broadcast shall be issued per incident.
End-of-Day Interim Broadcast
For incidents that remain active at the end of the operational day, the system shall flag open incidents for inclusion in the end-of-day batch review queue.
The Duty Manager reviews and approves dispatch for each flagged incident

Occurrence Log
The Occurrence Log is a standalone module for recording events and interactions that fall under IOH responsibility but do not meet the threshold for a formal incident, fault, or task. The module digitises existing hardcopy occurrence logbooks currently maintained by the IOH team, providing a searchable and filterable electronic record in place of the physical diary.
Occurrence records do not trigger a ground response, work order, or broadcast, and are not linked to the Case structure.
Common use cases include verbal interactions with members of the public, VIP and dignitary visit notifications, exercises, drills, and information dissemination activities.

Recipient Group Management
Distribution groups shall be managed as named collections of user email addresses, configurable by the System Administrator.
The system shall support creation, editing, and deactivation of distribution groups. 
Known standing groups include the Sentosa Crisis Operations Group and the SC Management Group.
On broadcast initiation, the system shall pre-populate the recipient field with the default distribution group mapped to the incident type and crisis level.
The Duty Manager or Controller may add or remove individual recipients prior to dispatch without modifying the group configuration permanently.
Broadcast Templates
The system shall support configurable broadcast templates mapped to incident type and crisis level.
